## 1. プロジェクト概要

### 1.1 プロダクト名

**Garage Connect**

### 1.2 ミッション

車屋（自動車整備工場・ディーラー）の顧客接点を **ハガキから LINE へ移行する** マルチテナント SaaS を提供する。

### 1.3 解く課題（一文）

> ハガキで送られる車検・点検案内は顧客に届かず、車屋は機会損失を、顧客は車検切れリスクを抱えている。

### 1.4 解決策（一文）

> 車屋ごとの LINE 公式アカウントから、顧客にパーソナライズされた通知を自動配信し、LIFF でワンタップ予約まで完結させる。

### 1.5 提供価値

**車屋への価値**
- ハガキ印刷・郵送コスト削減
- 反応率の高い顧客接点の獲得
- 失注の削減（他社で車検取られるのを防ぐ）
- 業務効率化（事務員の手作業削減）

**顧客への価値**
- 車検・点検の見落とし防止
- LINE で完結する予約体験
- 整備履歴がいつでも見られる安心感

## 2. 背景と課題

### 2.1 きっかけ

事業オーナーが、所有する社用車の車検切れに気づかなかった実体験。  
車検通知はハガキで送られていたが、他の郵便物に紛れて見落とされていた。

知人の車屋・ディーラーへのヒアリングにより、以下の業界実態が判明：
- 車検・点検案内は**ほぼ手作業 + ハガキ**で運用されている
- 顧客が見たかどうか確認できないため、結局電話フォローが発生
- 「ハガキを見ていない、別の業者に頼んでしまった」という機会損失が多い
- ハガキ印刷・宛名印刷・投函の事務コストが大きい

### 2.2 市場機会

- 全国の自動車整備工場：**約 9 万事業所**
- 大半が従業員 10 名以下の小規模事業者
- IT 投資が進んでおらず、紙運用が残る業界
- 既存の業務管理 SaaS（CarRide 等）は約 3,500 社導入＝**シェア 4% 程度、残り 96% が未開拓**

### 2.3 既存ソリューションの問題

| サービス | 問題点 |
|---------|--------|
| 大手業務ソフト（GATCH, 新一等書記官, Carフロンティア 等） | 6 年リース前提・初期数十万円・LINE 非対応・昭和的営業モデル |
| CarRide（業界価格破壊） | 月 6,000〜7,000 円と安いが、UI が古く、LINE 自動配信機能なし、顧客マイページなし |
| SMS 配信特化サービス | 配信のみで業務管理機能なし、SMS 単価が高い |

→ **「ハガキ → LINE への移行」に特化した軽量 SaaS は市場に存在しない**

### 2.4 仮説

「ハガキ案内をやめて LINE 自動配信したいが、業務全体の置き換えはしたくない」というニーズが、中小車屋に潜在的にある。  
月 2,000〜3,000 円の軽量 SaaS であれば、既存ソフトと併用で導入されうる。

## 3. プロダクトコンセプト

### 3.1 ポジショニング

> **「車屋の顧客接点を LINE に統一する、軽量マルチテナント SaaS」**

CarRide 等の既存ソフトが「**整備士の事務処理**」を担うのに対し、Garage Connect は「**車屋の顧客接点**」を担う。

両者は補完関係にあり、共存可能。

### 3.2 差別化の三本柱

1. **LINE 起点の顧客体験**
   - 既存ソフトは紙・メール前提
   - Garage Connect は通知・予約・契約・履歴閲覧をすべて LINE で完結

2. **軽量・低価格**
   - 月 3,000 円から、初期費用なし、契約縛りなし
   - 既存ソフト併用前提のため、置き換えコストが発生しない

3. **法人フリート管理**
   - 既存ソフトは個人顧客中心
   - 社用車を複数台保有する法人の管理に対応
   - 経理担当・運転者の分離通知

### 3.3 競合分析

| 比較軸 | Garage Connect | CarRide | GATCH |
|-------|---------------|---------|-------|
| 月額 | ¥3,000〜 | ¥6,000〜 | ¥9,800〜 |
| 初期費用 | ¥0 | ¥0 | リース契約 |
| LINE 自動通知 | ◎ | ✗ | ✗ |
| 顧客マイページ | ◎ | ✗ | ✗ |
| 車検証 QR 読取 | ◎ | ◎ | ◎ |
| 法人フリート管理 | ◎ | △ | △ |
| 整備管理（見積書・記録簿） | △ | ◎ | ◎ |
| 法定書類対応 | △ | ◎ | ◎ |
| マルチテナント・SaaS | ◎ | ◎ | ◎ |

→ **Garage Connect は「顧客接点」で勝ち、「事務処理」では戦わない**

## 4. 関係者

### 4.1 事業オーナー

- **役割**: 事業発想者、事業判断、営業・顧客開拓、ペルソナ顧客
- **担当**: 顧客ヒアリング、初期テナント獲得、価格戦略
- **強み**: 経営者ネットワーク、法人ユーザー視点
- **報酬形態**: 事業収益のレベニューシェア

### 4.2 開発担当

- **役割**: プロダクト企画、開発、技術判断
- **担当**: 設計、実装、保守、技術的意思決定
- **強み**: AI 活用による高速 SaaS 開発、業務システム設計経験
- **報酬形態**: 事業収益のレベニューシェア

### 4.3 アドバイザー（想定）

- **役割**: 業界知識提供、初期テスター
- **対象**: 知人の自動車整備工場・ディーラー
- **報酬形態**: MVP 期間中の無料提供 or 大幅割引

### 4.4 レベニューシェア条件（要別途契約書化）

以下は別途覚書で書面化する必要がある：
- 収益配分率

- 支払いタイミング
- 知的財産権の帰属
- 撤退条件
- 追加開発時の費用負担

## 5. ターゲット顧客

### 5.1 一次ターゲット

**従業員 10 名以下の地域整備工場・ディーラー**

特徴：
- 個人 + 法人 の混在顧客基盤を持つ
- IT 投資の予算は月 1〜2 万円程度
- 既存業務ソフトを使ってる、もしくは紙運用
- 経営者がデジタル化に前向き
- LINE 公式アカウントは未導入か、運用が止まっている

### 5.2 二次ターゲット

**フリーランス整備士・1 人事業主**

特徴：
- 開業 1〜5 年目
- ITリテラシーが比較的高い
- 業務ソフト未導入
- 顧客接点の獲得・維持が課題

### 5.3 ペルソナ（一次ターゲット例）

**A. 個人経営の整備工場**
- 経営者は 50 代男性
- 顧客 300〜500 件、車両 500〜800 台
- 月の車検入庫 30〜50 件
- 事務員 1 名がハガキ作成・郵送・電話対応
- 「ハガキ反応率が下がっている」「若い顧客は LINE がいい」と感じている

**B. 法人顧客**
- 内装会社、建設会社、運送会社など
- 社用車 5〜30 台
- 経理担当が車両管理を兼務
- 車検切れリスクが現実的に存在
- LINE 公式アカウントから通知が来れば運転者・管理者双方が把握できる

### 5.4 ノンターゲット（明示）

- 大手ディーラーチェーン（独自システム保有）
- 整備士不在の中古車販売店（メイン業務が異なる）
- 鈑金塗装専業店（業務フローが異なる）

## 6. 競合分析と差別化

### 6.1 直接競合

| サービス | 特徴 | 差別化のしどころ |
|---------|------|----------------|
| CarRide | 価格破壊、業界シェア急拡大 | LINE 非対応、顧客接点機能弱い |
| GATCH | 大手、機能豊富 | 高価格、リース契約、LINE 非対応 |
| 新一等書記官 | リピート獲得機能 | SMS のみ、月額数万円 |

### 6.2 間接競合

- ハガキ印刷代行業者（コクヨ等）
- SMS 配信サービス（Sマガ、メディアSMS）
- 汎用 CRM（HubSpot 等）

### 6.3 競合に勝つための戦略

1. **「全部入り」では戦わない**：CarRide 等と全機能で競合せず、顧客接点に特化
2. **既存ソフト併用前提**：置き換えコストを発生させない
3. **AI ネイティブな開発スピード**：競合の数倍のスピードで機能追加
4. **LINE プラットフォームへの深い統合**：通知だけでなく、予約・契約・履歴閲覧まで

## 7. 業務理解

### 7.1 車屋の収益構造（典型例）

```
車検（2〜3 年に 1 回、1 台 5〜15 万円）         30〜40%
点検・整備（12 ヶ月点検、修理）                 25〜35%
車販（新車・中古車）                          15〜25%
保険（自賠責・任意）                           5〜10%
鈑金塗装                                     5〜15%
```

**車検は最大の収益源かつ最強の顧客接点**。ここを取られると他も失う。

### 7.2 車検入庫の典型フロー

```
1. 来店 or 引取（出張サービス）
2. 受付（車検証受領・走行距離記録・外観チェック）
3. 仮見積もり提示
4. 顧客同意（契約書サイン）
5. 24 ヶ月点検（or 12 ヶ月点検）実施
6. 追加整備発見 → 顧客に連絡 → 承認取得
7. 整備完了
8. 完成検査
9. 陸運局へ書類提出（OSS or 持込）
10. 新車検証受領・顧客に返却
11. 請求・代金回収・次回車検日 DB 登録
```

### 7.3 既存の車検案内業務フロー（紙運用）

```
60 日前 → リスト出力 → ハガキ印刷 → 宛名印刷 → 投函
30 日前 → 反応ない顧客にリマインドハガキ
15 日前 → まだ反応ない顧客に電話
0 日前  → 失注 or 飛び込み入庫
```

### 7.4 Garage Connect が置き換える業務フロー

```
60 日前 → 自動 LINE 通知（仮予約ボタン付き）
45 日前 → 反応ない顧客にリマインド通知
30 日前 → 自動電話リスト出力
       → 予約済み顧客には事前見積・必要書類案内
入庫前 → リマインダー通知
入庫日 → 受付 QR・進捗通知
完了後 → サンクスメッセージ + 次回予約予告
```

### 7.5 通知トリガーの種類

車検以外にも複数のトリガーがある：

| トリガー | 周期 | 配信タイミング |
|---------|------|--------------|
| 車検満了 | 2〜3 年 | 60 / 45 / 30 日前 |
| 法定 12 ヶ月点検 | 1 年 | 30 日前 |
| 法定 6 ヶ月点検（事業用） | 6 ヶ月 | 30 日前 |
| メンテナンスパック点検 | 契約に応じる | 契約に応じる |
| 自賠責保険満了 | 車検と同期 | 30 日前 |
| 任意保険満了 | 1 年 | 30 日前 |
| オイル交換時期 | 6 ヶ月 or 5,000km | 推定到達時 |
| タイヤ交換（季節） | 6 月 / 11 月 | 該当月 |
| リコール対象通知 | 随時 | メーカー通達時 |

### 7.6 関連書類

車検・点検業務で使う書類：
- 法定書類: 自動車検査票、自動車重量税納付書、印鑑証明、委任状、保管場所証明、譲渡証明書
- 整備関連: 見積書、整備記録簿（指定整備・特定整備）、請求書、領収書、預かり証
- 車販関連: 車両注文書、車両請求書、契約書、リサイクル預託金、古物台帳

MVP では「請求書・契約書 PDF の保存」のみ対応。法定書類生成は Phase 2 以降。

## 8. ユースケース

### UC-1: 新規顧客登録（店側起点）

**アクター**: 店舗ユーザー

**前提**: 顧客が来店し、車検証を持参している

**フロー**:
1. 店舗ユーザーが管理画面で「新規顧客登録」を開く
2. タブレット / PC のカメラで車検証の QR コードをスキャン
3. システムが車両情報・所有者情報を自動入力
4. 店舗ユーザーが顧客の電話番号・LINE 連携用 QR を提示
5. 顧客が LINE 公式アカウントを友だち追加
6. システムが LINE User ID と顧客レコードを紐付け
7. 完了通知が顧客の LINE に届く

**事後条件**: 顧客と車両が DB に登録され、車検満了日に基づく自動通知が有効化される

### UC-2: 車検案内自動配信

**アクター**: システム（バッチ）

**前提**: 車両に車検満了日が登録され、顧客が LINE 連携済み

**フロー**:
1. 毎日 09:00 にバッチが起動
2. 全テナント × 全車両を走査
3. 車検満了 60 / 45 / 30 日前の車両を抽出
4. 該当顧客の LINE User ID を取得
5. テナント設定の通知テンプレを使って Flex Message を生成
6. LINE Messaging API で送信
7. 配信ログを記録

**事後条件**: 顧客の LINE に通知が届き、配信ログが残る

### UC-3: 顧客による予約（LIFF）

**アクター**: 顧客

**前提**: 車検案内通知を受け取った

**フロー**:
1. 通知メッセージの「予約する」ボタンをタップ
2. LIFF アプリが起動
3. 日時を選択（カレンダー UI）
4. 確認画面で内容確認
5. 「予約確定」をタップ
6. 予約が DB に登録され、店舗側に通知
7. 顧客の LINE に予約確定通知が届く

**事後条件**: 予約が `pending` 状態で登録され、店舗側で確認待ちとなる

### UC-4: 法人顧客の複数車両管理

**アクター**: 店舗ユーザー、法人顧客の経理担当

**前提**: 法人顧客が複数の社用車を保有

**フロー**:
1. 店舗ユーザーが顧客を `corporate` 種別で登録
2. 複数の車両を同一顧客に紐付け
3. 経理担当・運転者などの追加連絡先を登録
4. 通知配信時、車両ごとに該当者へ配信
5. 経理担当は全車両の状況を LIFF マイページで一覧確認

**事後条件**: 法人の車両状況が一元管理される

### UC-5: 既存システムからのデータ移行

**アクター**: 店舗ユーザー、開発担当

**前提**: 既存業務ソフトに顧客・車両データが蓄積されている

**フロー**:
1. 店舗ユーザーが既存ソフトから顧客・車両データを CSV エクスポート
2. Garage Connect 管理画面でテンプレ CSV をダウンロード
3. 列マッピング後、CSV をアップロード
4. システムがバリデーション
5. エラーがあれば修正案を提示
6. 確認後、一括登録

**事後条件**: 既存顧客が Garage Connect に移行される

## 10. 非機能要件

### 10.1 パフォーマンス

- 管理画面：初回ロード 3 秒以内、操作レスポンス 1 秒以内
- LINE 通知配信：1 テナント 1,000 件を 5 分以内に配信完了
- DB クエリ：99 パーセンタイル 500ms 以内

### 10.2 可用性

- 月間稼働率 99.5% 以上
- 計画メンテナンスは事前告知

### 10.3 セキュリティ

- 通信は HTTPS 強制
- データベースは Supabase の暗号化保存
- LINE Channel Token は `pgcrypto` で暗号化
- パスワードは Supabase Auth のハッシュ化
- RLS によるマルチテナント分離
- 全アクセスログ保持

### 10.4 マルチテナント分離

- テナント間のデータアクセスは絶対に発生しない
- E2E テストで定期的に検証
- 万一の漏洩リスクに備え、テナント間 ID 推測不可能（UUID）

### 10.5 スケーラビリティ

- 初期：100 テナント想定
- 1 年後：1,000 テナント想定
- Supabase は Pro プラン以上で対応可能

### 10.6 監査ログ

- 顧客データの変更履歴を保持（Phase 2）
- 配信ログは無期限保持

### 10.7 バックアップ

- Supabase の自動バックアップ（PITR）
- 重要データの月次エクスポート

## 11. 技術アーキテクチャ概要

### 技術スタック

- **フロントエンド**: Next.js 14 + TypeScript + shadcn/ui + Tailwind
- **バックエンド**: Supabase (PostgreSQL + Auth + Storage + Edge Functions)
- **外部サービス**: LINE Messaging API + LIFF + Stripe
- **インフラ**: Vercel + Supabase Cloud

### マルチテナント設計

Shared Database / Shared Schema + Row Level Security による論理分離。

### テナント別 LINE 公式アカウント

各テナントが個別に LINE 公式アカウントを取得し、Channel Token を管理画面で登録。トークンは `pgcrypto` で暗号化して DB 保存。

- プライバシーポリシー必須
- 利用目的の明示、同意取得
- 漏洩時の報告体制

- 請求書・領収書 PDF は検索可能形式で 7 年保管
- タイムスタンプ or 訂正削除履歴の保持

### 14.3 特定電子メール法

- メール送信時は配信停止リンク必須
- LINE は適用外

### 14.4 LINE 利用規約

- 商用利用は公式アカウントの該当プラン契約必須
- メッセージ配信上限に注意

### 14.5 古物営業法

- 中古車販売対応時（Phase 3 以降）に必要
